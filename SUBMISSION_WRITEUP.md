# AccessAid Agent — Submission Write-Up

## Problem Statement

Millions of people with visual impairments, cognitive disabilities, or low digital literacy struggle to use government forms, healthcare documents, and web content that was never designed for accessibility. Complex jargon, poor contrast ratios, unlabelled form fields, and non-navigable table structures create barriers that exclude people from critical services.

**AccessAid** directly addresses this problem by converting any complex document or form content into a screen-reader friendly, simplified, high-contrast accessible format — automatically, securely, and with human verification built in.

---

## Solution Architecture

```
START → 🔐 security_checkpoint → 🧠 orchestrator_node → ✋ human_approval_node → ✅ final_output_node
                │                         │
             BLOCKED                   (delegates to)
                │                    📄 document_analyzer_agent  ←──── MCP Server
                ▼                    📝 accessibility_summarizer_agent ← MCP Server
        ⛔ security_violation_node
```

The agent is built as a **graph-based ADK 2.0 Workflow** with:
- Deterministic routing at every decision point
- Human-in-the-loop (HITL) verification before final output
- Security checkpoint at the entry of every run
- MCP server providing domain-specific accessibility tools

---

## Concepts Used

### ✅ ADK Multi-Agent (Workflow Graph)
- **File:** `app/agent.py`
- `Workflow` graph with `@node`-decorated function nodes and routing via `RoutingMap` dicts
- 1 orchestrator (`orchestrator_agent`) + 2 specialized `LlmAgent` sub-agents
- `AgentTool` used by orchestrator to delegate to sub-agents
- `ctx.state` for inter-node data sharing (`raw_input`, `accessibility_report`, `pii_redacted`)
- `RequestInput` for HITL pause in `human_approval_node`

### ✅ MCP Server
- **File:** `app/mcp_server.py`
- Implemented using `FastMCP` (stdio transport)
- 3 domain-specific tools:
  1. `simplify_text_vocabulary` — replaces complex words with plain English
  2. `check_contrast_ratio` — WCAG contrast calculation for visual accessibility
  3. `format_screen_reader_table` — converts Markdown tables to linear screen-reader narration
- Wired into both `document_analyzer_agent` and `accessibility_summarizer_agent` via `McpToolset`

### ✅ Security Checkpoint
- **File:** `app/agent.py` — `security_checkpoint()` node
- Positioned directly after `START`, before any LLM processing
- See Security Design section below

### ✅ Agents CLI
- Scaffolded with: `uvx google-agents-cli scaffold create accessaid-agent --agent adk --deployment-target agent_runtime`
- `GEMINI.md` generated by scaffold (AI coding context)
- `make playground` target in `Makefile`
- Config in `app/config.py` using `GEMINI_MODEL` env var

## Security Design

| Control | Implementation | Why It Matters for Accessibility |
|---|---|---|
| **PII Scrubbing** | 7 regex patterns: email, phone, SSN, credit card, national ID, DOB, IP | Accessibility documents often contain patient/citizen personal data that must never be forwarded to LLMs |
| **Prompt Injection Detection** | 13 keyword patterns: `ignore previous instructions`, `jailbreak`, `act as`, `sudo`, etc. | Prevents malicious actors from hijacking the agent's accessibility workflow to perform unauthorized actions |
| **Content Policy Rule** | Min 5 words / Max 50,000 chars | Prevents empty submissions and DoS-style oversized inputs from exhausting API quota |
| **JSON Audit Log** | Every checkpoint decision emits `{timestamp, severity, event, detail}` | Creates a full audit trail for compliance — essential in healthcare/government accessibility contexts |

Security checkpoint routes: `SAFE → orchestrator` / `BLOCKED → security_violation_node` (unconditional, no LLM call made)

## MCP Server Design

| Tool | Purpose | Used By |
|---|---|---|
| `simplify_text_vocabulary` | Replaces jargon with plain English (12 substitution rules) | `document_analyzer_agent`, `accessibility_summarizer_agent` |
| `check_contrast_ratio` | Calculates WCAG 2.1 contrast ratio; reports AA/AAA compliance level | `document_analyzer_agent` |
| `format_screen_reader_table` | Converts Markdown tables into linear narrated rows for screen readers | `accessibility_summarizer_agent` |

All tools are pure Python, deterministic, and do not call external APIs — ensuring fast, offline-capable operation.

## HITL Flow

The `human_approval_node` pauses the workflow after the orchestrator generates the accessibility report:

1. Agent generates report via orchestrator + sub-agents
2. **Workflow pauses** — emits `RequestInput` with the full report and a verification prompt
3. Human reads the generated accessible content and replies `approve` or `reject`
4. On `approve` → `final_output_node` delivers the report
5. On `reject` → workflow loops back to `orchestrator_node` to regenerate

**Why HITL?** Accessibility outputs directly affect disabled users' ability to access critical services. A human expert (accessibility specialist, document owner) must verify quality before the output is delivered.

## Impact / Value Statement

**Who benefits:**
- **Visually impaired users** — documents become screen-reader navigable with proper heading structure and table narration
- **Cognitively disabled users** — complex jargon is automatically simplified to plain English
- **Low-literacy users** — step-by-step form instructions replace complex government/healthcare language
- **Accessibility specialists** — the HITL flow means experts review and approve output before it reaches end users
- **Organisations** — built-in audit logs support WCAG compliance documentation and data protection requirements

**Why it matters:**
Digital accessibility is a legal requirement in most jurisdictions (WCAG 2.1, ADA, EN 301 549) and a fundamental human right. AccessAid lowers the barrier to compliance for document owners while directly improving the lived experience of millions of users who depend on assistive technology every day.
